> 本文是一次还没排期落地的重构设计。文中“名单十万行”为实测数据；序列化体积、回源耗时等为基于代码走查的估算，不是压测结果；“效果”一节来自推演而非线上 A/B。之所以提前写下来，是因为这次推导过程比结论本身更值得沉淀。

## 一、先看清楚：这是几次等值判定，不是一次全表检索

风险名单（黑名单）是风控审批链路里的基础数据。它的匹配语义是这样的：

给定一笔进件，按 **姓名 / 身份证 / 手机号 / 收货地址** 分维度各撞一下，任一维度命中即视为命中；每个维度独立产出规则参数，并记录命中类型。

换句话说，这本质上是 **3~4 次等值判定**，不是一次"在名单里找有没有这个人"的检索。

这个认知很关键，因为线上原来的实现是反着的——它把"等值判定"实现成了"全表检索"。

## 二、症状：一条名单变更，让下一个不相干的请求去扫全表

原实现把所有 `status = EFFECTIVE` 的记录序列化成一个 `List`，缓存在一个固定 Key 下：

```java
@Cached(name = CacheConstants.RISK_ANTI_FRAUD_LIST_CACHE, key = "'EFFECTIVE'")
public List<RiskListDO> listEffective() { ... }
```

调用方拿到整表之后，在自己的内存里 `for` 循环匹配。

于是每次新增、修改、批量导入或删除任意一条记录，整份缓存失效；下一次进风控的订单，要在**自己的请求线程里**同步完成：全表查询 → 结果集传输 → MyBatis 映射十万个对象 → 序列化写回 Redis。

一条数据的变更，把成本转嫁给了另一个完全不相干的用户请求。

## 三、逐条定位

### 1. 缓存粒度与实际读写粒度错配

名单十万行（实测），单个 value 按 JDK 序列化估算约 30~50MB。而查询侧只做几个字段的点查——**存储的是整表，消费的是几个 key**。每次调用都要 GET 并反序列化十万个对象，附带大对象 GC 开销。

### 2. 失效后的回源是同步全表加载

`status` 列只有两个取值，选择性极低，缺索引时优化器大概率直接全表扫描。十万行扫一遍再序列化，按走查估算在秒级。并发下多个请求会**同时全表回源**（缓存击穿），把数据库打满——表现为接口尾延迟抖动，而抖动的原因和触发的那个请求毫无关系。

### 3. 失效覆盖是“逐个方法加注解”的约定

这一条准确地说不是现存缺陷，而是一份隐式契约：`@CacheInvalidate` 逐个重写在 DAO 的 5 个写方法上——`save`、`saveOrUpdateBatch`、`updateById`、`removeById`、`clearCache`。

核查过写路径：`RiskListRepositoryImpl` 的新增、更新、删除、批量导入都走了这几个方法，**当前没有绕过失效的入口**。

风险在于它依赖“写方法清单保持完整”这个约定。`ServiceImpl` 继承来的 `update(Wrapper)`、`updateBatchById` 等方法不带注解，以后若有人用它们写入，失效会被静默跳过。这是约定，不是机制，没有编译期保护。

### 4. 失效与事务提交之间的时序窗口

写路径由框架的 `DbRepository` 包装，而 `@CacheInvalidate` 在 DAO 方法返回时就会执行。如果这个时间点落在事务提交之前，窗口内进入的并发请求会读到未提交的旧数据，再把它写回缓存。

这条我无法只凭注解判定，取决于框架事务切面与缓存切面的先后顺序，需要单独验证。但即使窗口存在，后果也不是永久性的——见下一条。

### 5. 缓存层没有 TTL，但被“定时失效”兜住了

`@Cached` 没有声明 `expire`，所用 JetCache 2.6.0 的默认 `expireAfterWriteInMillis = 2147483647000`，约等于 **68 年不过期**。乍看很危险，但实际上不会出现“脏快照永久驻留”：

- **到期任务**：`riskListExpireJob` 跑到期名单，`RiskList::expire()` 之后走 `saveOrUpdateBatch`——同样带 `@CacheInvalidate`。这个任务在调度中心按天配置，也就是说缓存每天至少被整体清一次；
- **手动入口**：`PUT /clearCache` 提供了人工清缓存的兜底。

所以真正的问题不是“缓存会永久脏”，而是：**失效机制是完整的，代价是全量的。** 每一次失效都意味着下一个请求同步重建整表——这个动作每天至少发生一次，外加每一次名单写入。

## 四、一个被忽略的前提：写入其实是流量驱动的

原始设计有个隐含假设——“名单低频写，所以可以容忍整表失效”。这个假设需要验证，而验证的结果是它不成立。

名单写入有两类：

- 运营侧维护：人工录入、Excel 批量导入，频率确实低；
- **业务流量驱动的自动写入**：命中某类三方黑名单时，前置规则会同步把该用户写进内部名单，有效期 999 天。

也就是说：

```
失效频率 = 命中率 × 订单量
```

失效不再是低频事件，而是随订单量波动的常态。再叠加“有效期 999 天”只增不减的特性，O(N) 的成本会持续恶化。**按“低频写”设计的缓存，被高频写穿透了。**

## 五、决定方案走向的其实是容量：先算数，再决定要不要缓存

在动手改缓存之前，先回答一个问题：这个查询，到底需不需要缓存？

- 名单规模：**十万行（实测）**，按序列化估算整表约 30MB —— 可以完整常驻 InnoDB buffer pool；
- 订单峰值点查：估算在几十 ~ 两百次/秒。而同体量下单实例 MySQL 的索引点查能力是**上万次/秒**。

两者相差**两个数量级**。

结论：查询根本不需要“把缓存当数据源”，索引点查本身就是最优解。缓存只该用来兜住“值得兜的那一小部分”。

这也解释了为什么之前所有优化都别别扭扭：**在一个不需要缓存的查询上做缓存优化，方向本身就是错的。**

## 六、方案：数据源回归 DB，缓存只保留“命中”这一侧

### 6.1 第一步：把 list 从缓存里拿掉

删除 `listEffective()` 上的整表快照，同时删掉挂在写方法上的 `@CacheInvalidate` 和 `clearCache()` 的失效语义。

整表失效这套机制随快照一起去掉。单条变更不再触发全表失效，也不必再处理失效时序、TTL、击穿保护这一整类问题——**它们不是被解决了，是被消灭了。**

### 6.2 第二步：点查下沉到 DB，并补齐支撑索引

按维度点查，条件里带上生效语义：

```sql
ALTER TABLE risk_list
  ADD INDEX idx_mobile_status_expire (mobile_phone, status, expire_date),
  ADD INDEX idx_idcard_status_expire (id_card,    status, expire_date),
  ADD INDEX idx_name_status_expire   (full_name,  status, expire_date);
```

维度列在前、过滤条件在后：等值列负责定位，`status` / `expire_date` 在索引内完成过滤，不必回表。

一份进件的多个维度分别点查，在应用层做并集——语义与原来的全表遍历完全一致。

### 6.3 第三步：缓存只上“命中”这一侧

命中名单是少数，命中结果才值得缓存。而且**这层缓存的 Key 空间由名单规模决定，与查询量无关**：

```text
rl:v:{listType}:{attr}:{归一化值}  ->  listId（或命中明细）
```

三条设计约束：

- **只在查到命中时写入**。未命中不写空值——DB 点查撑得住，不需要负缓存挡穿透；更重要的是，未命中的取值空间由**进件量**决定，可能是名单量的几十倍，一旦写进去，Redis 内存就被绑到历史进件量上了。
- 命中是少数，按 `listId` 回表取明细的成本可以忽略。
- Key 上带 TTL，但**只作性能兜底**：缓存丢了或脏了，回源 DB 点查即可。最坏影响是性能，不会误杀或漏放——这一点决定了这层缓存不需要复杂的可靠性设计。

### 6.4 写入路径

```text
写 DB → COMMIT → afterCommit 中按新值「覆盖」对应 Key
```

几个必须守住的细节：

- **覆盖，而不是先删后写**。先删会在删除到写入之间留出空窗，被并发回源写回旧值。
- **扇出**。横表的一行要扇出成它所有非空维度的 Key；空值必须跳过，否则所有空值记录会互相命中。
- **改 / 删要同时覆盖新旧两套维度的 Key**。手机号从 A 改成 B，A 的 Key 也要删掉。
- **归一化读写必须用同一个函数**（手机号去 `+86` 和空格、身份证 15 位补位、`x` 统一成 `X`、姓名去空白并统一全半角），否则索引两侧永远对不上。

## 七、顺手修掉的三处语义缺陷

排查同一条查询链路时，发现三个和缓存粒度无关、但更危险的问题：

1. **过滤条件与领域模型不一致**：查询只过滤 `status`，不过滤 `expire_date`，而领域对象的生效判定是两者都满足。到期任务又按“`expire_date` = 当天”等值查询，本身不幂等。一旦任务漏跑一天，过期记录会永远停在生效状态——**持续误杀，且无告警**。
   → 查询条件补上 `expire_date`；到期任务改为 `expire_date <= 当天 AND status = EFFECTIVE`，使其可补跑、可重入。

2. **状态列比较依赖全局 TypeHandler**：查询用枚举直接和 String 列比较，一旦有人把全局映射改成 ordinal，会**静默返回空名单**——漏放，且没有任何异常。
   → 显式使用枚举 `name()` 比较。

3. **在线链路里还在拉全量名单**：订单侧以空条件拉取生效列表；某些需要全量候选的规则，在线逐条遍历全表。
   → 订单侧改为按维度点查、只取命中项；需要全量候选的规则，先用表里已有的地理哈希列做桶点查收敛候选（九宫格邻域）再算精距离，或移出在线链路走离线特征。

第 1 条尤其值得记一笔：**它不是一个性能问题，是一个资金问题。** 缓存重构顺带把它挖出来了。

## 八、前后对比

| 维度 | 改造前 | 改造后 |
| --- | --- | --- |
| 单次查询 | 拉全量 + 反序列化十万对象 + 内存 O(N) 遍历 | 3~4 次索引点查（亚毫秒级） |
| 单个 Key value | 约 30~50MB（估算） | 几十 ~ 几百字节 |
| 一条名单变更的代价 | 全表失效 → 下一个请求同步重建整表 | 只覆盖该记录涉及的几个维度 Key |
| 整表失效频率 | 每次写入 + 到期任务每天一次 | 不再有整表失效 |
| 缓存内存取决于 | 查询量 / 进件量 | 名单规模 |
| 一致性风险 | 失效时序窗口、永不过期的 TTL | 随整表快照一并消失（缓存可随时丢弃） |

最关键的变化不是“变快了”，而是**读路径和写路径解耦**：一条名单变更只影响它涉及的几个 Key，名单随命中量增长时，写入成本不再随之线性上升。

## 九、几条可迁移的判断

1. **先算容量，再决定要不要缓存。** “这个查询要不要加缓存”是个数学问题，不是习惯问题。数量级对不上，方向就是错的。
2. **缓存的粒度要匹配读写的粒度。** 缓存里存了整表，消费的却是几个字段——这就是粒度错配，迟早以击穿、尾延迟抖动、脏数据的形式还回来。
3. **想清楚缓存“丢了会怎样”。** 如果答案是“最坏只是慢一点”，这层缓存就可以做得很简单；如果答案是“会算错”，那它就不是缓存，是数据源——那你就得按数据源的可靠性标准去建设它。
4. **别用注解缓存去兜一个本该由索引解决的查询。** 注解式缓存容易写，但它会诱导你绕过对数据模型本身的思考。
5. **在改一个东西之前，先把它的假设验证一遍。** 这次真正的转折点是“名单低频写”这个前提被证伪：既然写入是流量驱动的，那所有基于“低频写”的设计都失去了地基。
6. **失效机制“完整”不等于“没问题”。** 这套缓存的失效覆盖其实是完整的——每条写路径都失效、每天还有定时兜底、甚至留了手动入口。但正因为失效的粒度是整表，机制越完整，“全量重建”发生得就越频繁。**覆盖率不是缓存设计的终点，粒度才是。**
